# HomeRadar — замена выгрузки Apify

## Установка

Нужен Python 3.11+. Зависимости перечислены в `pyproject.toml`.
В PowerShell из папки репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install .
.\.venv\Scripts\python.exe -m playwright install chromium
```

## Собрать организацию и получить файл для проверки импорта

```powershell
.\.venv\Scripts\python.exe export_homeradar.py 79619695705 --output review_results/homeradar/79619695705.json
```

Вместо ID можно передать полную HTTPS-ссылку на организацию в `yandex.ru/maps/org/…`.
Экспорт HomeRadar запускает реальный Chromium через существующий `collect_yandex.py`.
Публичные HTML-страницы используются дополнительно для аватаров и ответов организаций.
Параметр `--executable` задаёт путь к установленному Chrome/Chromium.

Готовый файл: **`review_results/homeradar/79619695705.json`**.
Каждый запуск заново читает все страницы карточки, а не выдаёт вчерашний кэш.
Код выхода `0` и событие `homeradar_export` означают успешный экспорт текущего запуска.
При ненулевом коде выхода прежний файл может существовать: это не результат текущего запуска,
его нельзя считать свежим или автоматически импортировать после ошибки.

## Контракт импорта

Корень — JSON-массив. Каждая запись содержит ровно эти девять полей:

```json
[
  {
    "businessRating": 4.7,
    "businessRatingsCount": 499,
    "text": "Вымышленный пример отзыва.",
    "rating": 5,
    "date": "2026-10-01T12:00:00Z",
    "authorName": "Тестовый автор",
    "authorAvatarUrl": "",
    "businessComment": "Спасибо!",
    "businessCommentDate": "2026-10-02T12:00:00Z"
  }
]
```

- `businessRating` — общий рейтинг Яндекса с точностью до одного десятичного знака,
  не среднее по скачанным отзывам.
- `businessRatingsCount` — общее количество **оценок**, не число текстовых отзывов.
- Общие показатели повторяются в каждом элементе, поскольку импортёр читает их из первого.
- Даты — ISO 8601 UTC; используется `updatedTime` источника (дата последнего изменения).
- Отсутствующие аватар и ответ — пустые строки; существующие ответы и аватары не заменяются заглушками.
- В массив не добавляются служебные ID, статусы или другие поля вне согласованного контракта.
  При импорте организация определяется сохранённым в WordPress ID Яндекс Карт,
  соответствующим ID в команде запуска.

## Что адаптировано

`export_homeradar.py` использует существующий браузерный сборщик как основной источник
подтверждённых текстов, оценок, дат, авторов и показателей карточки. Дополнительный источник —
JSON-состояние публичных HTML-страниц Яндекса; это не официальный API.

1. Запускает полный Chromium-сбор с `--refresh`, без повторного использования вчерашнего кэша.
2. Получает аватары и ответы из всех объявленных публичных HTML-страниц через `StateScript`,
   проверяя номер страницы, смещение, размер порции и общий счётчик.
3. Сопоставляет записи по исходному ID либо однозначному полному содержимому;
   проверяет даты, оценки, полноту и одинаковые общие показатели двух проходов.
4. Сохраняет браузерный снимок, дополнительные поля и существующие диагностические логи
   для автономной проверки и повторного экспорта.
5. Записывает массив существующей атомарной функцией `storage.save_result` только после всех проверок.
   Существующая блокировка `storage.output_lock` исключает одновременные экспорты в одну папку.

Служебные данные остаются рядом с выгрузкой:

```text
review_results/homeradar/
  79619695705.json
  work/79619695705/
    raw/79619695705.json
    public-details.json
```

Весь `review_results/` исключён из Git: реальные отзывы, локальные пути и диагностические файлы
не публикуются с исходниками. В тестах используются только вымышленные отзывы.

## Безопасное обновление

При CAPTCHA, HTTP 403/429, незавершённом сборе, дубликатах, отсутствующих обязательных полях,
неоднозначном сопоставлении и изменении показателей между проходами команда завершается ошибкой.
В HomeRadar-сценарии HTTP 429 не повторяется автоматически. Между дополнительными
HTML-страницами предусмотрена пауза 1 секунда; их сетевой запрос ограничен 30 секундами.
Chromium-проход и дополнительный HTML-проход имеют отдельные ограничения времени;
ежедневный координатор дополнительно ограничивает весь сбор и отмечает невыполненную очередь.
При сетевом обрыве, таймауте или HTTP 502/503/504 повторяется только текущая GET-страница
и только один раз после паузы 2 секунды. Ошибки данных и ограничения доступа не повторяются.
Неполная выгрузка не публикуется даже если Яндекс ограничивает доступное число отзывов.

Карточка без отзывов тоже не перезаписывает готовый файл: `[]` не может передать рейтинг и число оценок
импортёру, который читает их из первого элемента. Для такого случая нужен отдельно согласованный
контракт WordPress. Отсутствующий общий рейтинг не подменяется нулём.

Ошибки отдельных источников остаются явными: отсутствие общего рейтинга, пустые/неполные карточки,
расхождения счётчиков, неоднозначные соответствия и ограничения доступа не превращаются в успех.
Старые файлы и ранее импортированные отзывы при отказе не заменяются частичными данными.

## Ежедневный сбор и доставка

`.github/workflows/daily-update.yml` запускает **HomeRadar daily update** ежедневно
в **03:17 Europe/Moscow**: `17 0 * * *` в UTC. Сбор выполняется и без настроенного приёмника.
Запуск разрешён также вручную: **Actions → HomeRadar daily update → Run workflow**.

- `organization_ids` — ID Яндекс Карт через пробел; пустое поле означает весь реестр компаний.
- `dry_run` по умолчанию включён для ручного запуска: проверяет подготовленные данные без POST
  и без передачи токена процессу. Для реальной отправки с `main` его нужно выключить.
- Плановый запуск отправляет проверенные результаты автоматически, когда настроены оба параметра
  приёмника. Если оба отсутствуют, режим явно остаётся `collect-only`; сайт не меняется.
- Отправка разрешена только с `main`. Запуск с другой ветки может собирать данные, но не получает
  параметры приёмника и не выполняет шаг доставки.

Реестр берётся из опубликованных записей `company` WordPress REST с проверкой пагинации
и общего количества, а не только из SEO sitemap. На исходной проверке 30.10.2026 REST содержал
258 компаний, `company-sitemap.xml` — 220: sitemap не доказывает полноту каталога.
Количество не зашито в код: каждый запуск заново читает актуальный реестр и страницы компаний.
Отсутствующий или неоднозначный ID фиксируется как ошибка; повторяющийся ID собирается один раз
с сохранением всех связанных страниц HomeRadar.

Локальные эквиваленты (для каждого нового сбора нужна новая папка):

```powershell
.\.venv\Scripts\python.exe run_homeradar.py collect --output review_results/daily-local
.\.venv\Scripts\python.exe run_homeradar.py deliver --output review_results/daily-local --dry-run
```

Выборочный сбор и отправка уже подготовленного результата:

```powershell
.\.venv\Scripts\python.exe run_homeradar.py collect --output review_results/daily-selected --organization 79619695705 243170996991
# Только после настройки согласованного приёмника и окружения:
.\.venv\Scripts\python.exe run_homeradar.py deliver --output review_results/daily-selected
```

Окружение доставки: repository variable `HOMERADAR_IMPORT_URL` и Actions secret
`HOMERADAR_IMPORT_TOKEN`. Не задавайте токен аргументом команды, в workflow-файле или артефакте.
Отсутствие обоих параметров разрешает сбор без доставки; наличие только одного — ошибка конфигурации.
До настройки приёмника новые отзывы **не попадают на сайт**. Настройка секретов, приглашения
collaborator и изменения сайта не выполняются этим кодом. Реализацию WordPress делает Александр,
приглашение collaborator отправляет владелец репозитория.

Сначала выполняются установка и автономные регрессионные тесты; их ошибки блокируют сбор
и доставку. У коллектора бюджет 315 минут, у шага сбора 317, у доставки 30, у job 350 минут.
Ежедневный workflow и прежний manual smoke используют общий `homeradar-live` с
`cancel-in-progress: false`, поэтому одновременно не собирают Яндекс.

Ненулевой код общего сбора не скрывается и оставляет workflow красным. После частичного сбора
доставка всё же обрабатывает только успешно проверенные файлы **этого запуска** из приватного
`manifest.json`; неподтверждённые, старые, изменённые и не попавшие в manifest файлы не отправляются.
Отсутствующий/повреждённый manifest — явная ошибка, не повод искать JSON по папкам.
При отмене job доставка не начинается. Ограничение времени или доступа оставляет невыполненные
организации видимыми в сводке; старые данные этих организаций на сайте сохраняются.

GitHub запускает cron на default branch, когда workflow уже находится в ней. Запуск может
задержаться или быть пропущен при нагрузке; в публичном репозитории расписание отключается
после 60 дней отсутствия активности. Это не гарантия точного времени или работы без обслуживания:
владелец контролирует запуски и при необходимости включает workflow снова. Искусственного
keepalive-коммита нет. [Ограничения расписания GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## HTTPS-контракт приёмника WordPress

Доставка делает `POST` на согласованный HTTPS endpoint. Тело запроса — **тот же неизменённый
legacy JSON-массив с девятью полями**, не новая обёртка. Служебные сведения передаются заголовками:

```text
Content-Type: application/json
Authorization: Bearer <HOMERADAR_IMPORT_TOKEN>
X-Homeradar-Organization-Id: <Yandex organization ID>
X-Homeradar-Run-Id: <run ID>
X-Homeradar-Content-SHA256: <SHA-256 exact request body bytes>
Idempotency-Key: <organization ID>:<SHA-256 exact request body bytes>
```

Успешный ответ должен иметь статус HTTP 200 и содержать JSON-подтверждение:

```json
{
  "organization_id": "79619695705",
  "status": "applied",
  "content_sha256": "<SHA-256 exact request body bytes>",
  "reviews_count": 123
}
```

`status` допускает только `applied` или `unchanged`; ID, SHA-256 и число отзывов должны точно
соответствовать запросу. Один HTTP 2xx без правильного подтверждения не означает успешный импорт.
Endpoint обязан проверить авторизацию, тело, связь организации с записью компании и затем
**атомарно заменить полный набор отзывов одной организации**. Ошибка валидации не должна стирать
предыдущий набор. Повтор с тем же `Idempotency-Key` должен быть безопасным и вернуть `unchanged`
без дубликатов. Это необходимо при сетевом обрыве после уже выполненной записи.

В JSON нет стабильных ID отзывов; добавление каждой строки к существующим данным не является
согласованным алгоритмом обновления. Внутренние таблицы, meta-поля и endpoint WordPress здесь
не угадываются: Александр реализует приёмник в существующей архитектуре сайта и возвращает
проверяемое подтверждение. Действующая Apify-интеграция этим изменением не отключается.

## Публичные отчёты и приёмка

Артефакт `homeradar-daily-summary` хранится три дня и имеет закрытый список файлов:

```text
review_results/daily/catalog.json
review_results/daily/collection/summary.json
review_results/daily/collection/summary.md
review_results/daily/delivery.json
review_results/daily/summary.md
```

Это только соответствия публичных страниц, статусы, коды причин и счётчики. Тексты отзывов,
имена авторов, аватары, ответы, полные JSON-выгрузки, `manifest.json`, raw-снимки, логи и кэш
не загружаются в публичные артефакты. Исходные логи сохраняются на временном runner для выполнения
сценария, существующее логирование не отключено. В Actions job summary добавляется только
безопасная Markdown-сводка, в том числе при ошибке; неуспех не маскируется зелёным статусом.

Этапы приёмки различаются:

1. Автономные тесты подтверждают валидацию, границы доверия и совместимость формата.
2. Ручной live-сбор подтверждает фактический источник на GitHub runner; отдельные отказы остаются отказами.
3. После установки workflow на `main` нужны **два фактических последовательных запуска по расписанию**
   со сверкой полноты реестра, текущих результатов и явных ошибок. Ручной запуск не заменяет cron.
4. После реализации и настройки приёмника нужна реальная проверка WordPress: применение,
   повтор без дублей, обновление дат/ответов и сохранение старых данных при отказе.

Наличие workflow и локальные тесты сами по себе не доказывают ни будущие запуски cron,
ни работающий импорт на сайт. До четвёртого этапа замена действующего импорта не принята.

## Повторить экспорт сохранённых данных без сети

```powershell
.\.venv\Scripts\python.exe export_homeradar.py 79619695705 --from-snapshot review_results/homeradar/work/79619695705/raw/79619695705.json --details review_results/homeradar/work/79619695705/public-details.json --output review_results/replay/79619695705.json
```

Этот режим не делает данные свежими; он предназначен для проверки адаптера и воспроизводимости.

## Тесты

Только адаптация, без сети и браузера:

```powershell
.\.venv\Scripts\python.exe -m unittest test_homeradar -v
```

Все тесты, включая исходные проверки в браузере на локальном HTML:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -v
```

Если вместо браузера Playwright используется установленный Chrome, перед полным прогоном задайте:

```powershell
$env:REVIEW_CHROMIUM_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
```

## Ручная проверка на GitHub Actions

Вкладка **Actions → HomeRadar manual smoke test → Run workflow** запускает
локальные регрессионные тесты на Ubuntu 24.04 и реальный CLI для десяти фиксированных
организаций из предыдущей проверки (`actions_smoke.CASES`). Карта и секреты сайта не используются.

Этот отдельный workflow — только ручная проверка, без отправки в WordPress;
ежедневный сценарий описан выше.
При CAPTCHA/HTTP 403/429 оставшаяся очередь останавливается.
Готовые JSON повторно сверяются существующим валидатором `build_export` с исходными данными.
Неполная выгрузка считается провалом, а не успешным пустым результатом.
Поэтому две ранее неподдержанные карточки также могут сделать весь workflow красным.

Публичный артефакт `homeradar-smoke-summary` содержит только количество записей,
общие показатели, длительность и статусы. Тексты отзывов, авторы, аватары и исходные логи
остаются в `review_results/` на временной машине runner и не загружаются в артефакты.
Сводка хранится три дня. Полные результаты с runner автоматически на сайт не передаются.

В поле `scope` можно выбрать `catalog`: это разовая проверка полного реестра `company`
WordPress REST, а не расписание. Страницы HomeRadar читаются последовательно;
отсутствующие/неоднозначные ID и ошибки страниц сохраняются в `catalog.json`.
Повторяющиеся ID проверяются один раз, с сохранением всех связанных URL сайта.
Проверка организаций идёт с паузой 20 секунд. При ограничении доступа очередь останавливается,
непроверенные карточки помечаются `not_run`, а частичный прогон не выдаётся за успех.
Публичная сводка содержит только счётчики полей и статусы, без текстов и авторов.
Один полный проход не доказывает стабильность ежедневных запусков или правильность WordPress-импорта.

Для повторной проверки проблемных карточек выберите `selected` и передайте их ID через пробел
в `organization_ids`. У отказов экспорта публикуется только код причины, например
`business_rating_unavailable`, без содержимого отзыва или полного сообщения исключения.
Соответствующий CLI: `python actions_smoke.py --organization 243170996991 19838055208`.
